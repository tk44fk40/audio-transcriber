# Lumi Companion 音声処理ライブラリ拡張 詳細設計書

## 1. 概要と目的

本ドキュメントは、`lumi_companion`（るみぽん！）における要件仕様書 [AUDIO_LIBRARY_REQUIREMENTS.md](https://github.com/tk44fk40/lumi_companion/blob/issue-5/feat-gemini-provider-poc/docs/AUDIO_LIBRARY_REQUIREMENTS.md) に準拠し、`audio-transcriber` のアーキテクチャを設計するための技術設計書です。

本ライブラリは、大きく分けて以下の **2つの異なるユースケース（入力フロー）** をサポートし、それぞれに最適化されたパイプラインを提供します。
1. **ストリーミング入力（ライブラリ利用）**: マイク等から随時入力される音声ストリームに対する低遅延・リアルタイムな文字起こし。
2. **ファイル入力（CLI / ライブラリ利用）**: 既存の音声・動画ファイルに対する高精度なマスタリング前処理と一括文字起こし。

---

## 2. アーキテクチャ構成（2つの入力フローの分離）

```mermaid
graph TD
    subgraph Input [入力]
        StreamIn["1. ストリーム入力\n(ライブラリ利用: feed_chunk)"]
        FileIn["2. ファイル入力\n(CLI / ライブラリ利用)"]
    end

    subgraph Pipeline [パイプライン処理]
        StreamPipe["AudioStreamPipeline\n・内部リングバッファ\n・マスタリング: スキップ\n・自前VAD(Silero)によるチャンク分割"]
        FilePipe["FileProcessingPipeline\n・マスタリング\n(RNNoise ➔ Gate ➔ Limiter)\n・Remux (動画トラック置換)"]
    end

    subgraph Core [推論コア (共通)]
        STT["SpeechTranscriber\n(Faster-Whisper)\n・モデル常駐・VRAM管理\n・チャンクごとの逐次推論"]
    end

    subgraph Output [後処理]
        PostProcess["後処理モジュール\n(Sanitizer ➔ PostProcess)"]
    end

    StreamIn --> StreamPipe
    FileIn --> FilePipe
    
    StreamPipe --> STT
    FilePipe --> STT

    STT --> PostProcess
```

## 3. 各機能の詳細仕様

### 3.1 共通コア: モデル常駐型推論 ＆ 共通データモデル
* **目的**: 毎回のモデルロードによる遅延を排除し、常駐型で低遅延な推論基盤を構築する。
* **対象ファイル**: `src/audio_transcriber/stt.py`, `src/audio_transcriber/models.py`
* **仕様**:
  * 初期化時に Faster-Whisper モデルおよび自前VAD（Silero-VAD）をロード・常駐化（Pre-warmed）する。
  * `faster-whisper` 内蔵のバッチ処理前提のVAD（`vad_filter=True`）は無効化し、システム側（各パイプライン）で音声区間を制御してチャンク単位で推論させる。
  * `unload()` / `close()` による安全な VRAM 解放。

### 3.2 【ストリーミング入力】 パイプライン仕様
* **目的**: リアルタイム音声チャンクの逐次投入、VADによる発話切り出し、および文脈を維持した低遅延な推論を行う。
* **対象ファイル**: `src/audio_transcriber/streaming.py`, `src/audio_transcriber/callbacks.py`
* **仕様**:
  * **ノイズ除去・マスタリングのスキップ（バイパス）**: ストリーミング音声は前段（OBSなど）ですでにノイズ除去等のエフェクト処理が掛かっている前提とします。そのため、二重処理による音質劣化（音痩せやアーティファクト）およびレイテンシの増加を防ぐため、本ライブラリ内でのノイズ除去およびマスタリング処理はストリーミング時には一切行わずバイパスします（※ファイル入力時のみ実行します）。
  * **チャンクの切り出しとタイムスタンプ管理**: 音声ストリームをリングバッファに貯め、自前VADが「発話の終わり（短い無音）」を検知した単位ごとに切り出して推論へ回します。ストリーミング時のタイムスタンプ（タイムコード）は原則として開始時を `0.0` 秒として算出しますが、親システム（OBSや配信基盤など）と時間を同期できるよう、**ストリーム開始時の初期タイムスタンプ（オフセット秒数）を外部からパラメータとして指定できる設計**とします。これにより、コールバックで返される絶対タイムコードを親システム側と厳密に一致させます。
  * **コンテキストの維持とハルシネーション対策**: 「固定プロンプト」と「過去の文脈」を合算した全体の文字数を監視し、上限（例: 200文字）を超える場合は「一番古い過去の文脈チャンク（文の塊）」から丸ごと破棄する。長めの無音（例: 3秒）を検知した場合は文脈をリセットする。
  * **長短チャンクの保護（VAD暴走対策）**: チャンクに「最大長（例: 30秒）」を設け、無音がなくても強制的に切り出して出力詰まりを防ぐ。同時に「最小長（例: 1.0秒）」を設け、短すぎるチャンクは次に結合して幻覚を防ぐ。
  * **非同期コールバック**: VAD 発話開始・終了検知と推論結果の確定時に非同期コールバック（`on_segment`, `on_vad_state_change` 等）を発火する。

### 3.3 【ファイル入力】 パイプライン仕様
* **目的**: 既存のファイルに対する S/N 比・解像度の向上（マスタリング）と一括処理。
* **対象ファイル**: `config.toml`, `config.py`, `pipeline.py`, `cli.py`, `rnnoise.py`
* **仕様**:
  * **マスタリング前処理**: FFmpeg フィルタチェーン（ノイズ除去 ➔ ノイズゲート ➔ 1段目リミッター ➔ ノーマライズ ➔ 最終リミッター）を直列連結して適用する。
  * **リアルタイム（逐次）出力**: CLI実行時であっても処理が終わるまで待たず、ストリーミング同様に遅延バッファリングを用いながら順次出力・補正処理を行う。
  * **Remux**: 動画ファイル入力時は、マスタリングされた音声トラックで動画を書き換える。

### 3.4 後処理およびサニタイズ仕様
* **対象ファイル**: `sanitizer.py`, `postprocess.py`
* **仕様**:
  推論によって確定した単一セグメントごとに、以下の後処理を順次適用して字幕やテキスト出力の品質を担保します。
  1. **無音・無効セグメントの破棄**: Whisperの無音確率（`no_speech_prob`）が閾値を超えている場合や、テキストが空（記号のみ等）のセグメントを除外します。
  2. **重複テキストの除去（ハルシネーション対策）**: Whisper 特有の無限ループ（同じフレーズの連続）や不自然な繰り返しを検知して間引きます。
  3. **カスタム辞書による用語置換**: ユーザー定義の辞書（設定ファイル等）に基づき、ゲーム用語やキャラクター名などの誤認識しやすい単語を正しい表記へ置換します。
  4. **テキストの正規化（オプション）**: 設定に応じて、英字の小文字化、または不要な句読点や記号の削除を行います。
  5. **字幕用のタイミング補正**: 短すぎる字幕の表示時間確保（`min_duration`）、発話終了後の余韻の付与（`end_padding`）、およびセグメント間のオーバーラップ（被り）防止等のタイミング補正を行います。

※ **【要件仕様に対する実装見送り事項】**: 要件仕様書で定義されていた「アラビア数字・ローマ数字・漢数字の正規化」については、本設計では明確に **やらない（実装を見送る）** ことと決定しました。

### 3.5 耐障害性とメトリクス通知（非機能要件）
* **対象ファイル**: `stt.py`, `streaming.py`, `callbacks.py`
* **仕様**:
  要件仕様書に基づく非機能要件として、以下の耐障害性および稼働監視の仕組みを実装します。
  1. **CUDA OOM（VRAM不足）耐性とリカバリ**:
     GPU メモリ不足例外（`OutOfMemoryError`等）発生時はシステムをクラッシュさせず、例外を安全に捕捉して `on_error` コールバックへ通知します。また、安全なメモリ解放や CPU 推論へのフォールバック等、処理を継続または安全に中断するためのリカバリ処理を行います。
  2. **メトリクスと稼働状況の定期通知**:
     パイプライン内で発生する処理レイテンシ（発話終了から字幕確定までの時間）や、内部リングバッファの未処理残量などの稼働状況を監視し、`on_metrics` コールバックを通じて外部システムへ定期的に通知します。

### 3.6 インターフェースとデータモデルの標準化
* **出力データモデル**: 要件仕様書に基づく標準化されたスキーマとして、認識完了時等のイベントには以下の `RecognizedSegment` データクラスを統一フォーマットとして出力します。

  ```python
  from dataclasses import dataclass, field


  @dataclass(frozen=True)
  class RecognizedSegment:
      text: str  # 認識・後処理完了済みテキスト
      raw_text: str  # 辞書置換前のWhisper生テキスト
      start_time: float  # 発話開始時刻 (秒)
      end_time: float  # 発話終了時刻 (秒: 余韻補正後)
      confidence: float  # 認識信頼度スコア (0.0〜1.0)
      is_final: bool  # 確定セグメントフラグ
      is_peak_sound: bool = False  # 叫び声・大音量SE検知フラグ (将来対応用)
      sound_events: list[str] = field(default_factory=list)  # 検知イベント (将来対応用)
  ```
* **ステータスクリア機能（リセット）**: 入力切替時や異常発生時に備え、非同期・スレッドセーフに状態を初期化できる `reset()` メソッドを提供します。これにより、内部のリングバッファ、VADのステート、履歴文脈（プロンプト）などを即座に破棄・クリア可能とします。

### 3.7 単体テスト性（テスト容易性）
* **デバイス・GPU非依存の検証**: デバイス（マイク）やGPUが存在しない環境（CI環境等）でも動作検証ができるよう、ダミーの音声波形データをパイプラインに直接投入可能なアーキテクチャとします。また、推論エンジンを Mock（ダミー）に差し替えられる DI（依存性の注入）構造を採用し、高品質な単体テストを維持可能にします。

### 3.8 推論エンジンの抽象化と切り替え（プロバイダーパターン）
* **STTプロバイダーのインターフェース化**: 音声認識を行う推論エンジンは、特定のライブラリ（`faster-whisper` 等）に密結合させず、共通の `TranscriberProvider` インターフェース（Protocol等）を実装する設計とします。
* **エンジンの差し替え**: これにより、ローカル環境で動作する `FasterWhisperProvider` や、外部のクラウドAPIを呼び出して処理するプロバイダー（Whisper API等）、さらにはテスト用の `MockProvider` などを同一インターフェースでシームレスに切り替え（DI）て利用することが可能になります。

## 4. ライブラリ利用を想定したパラメータ引き渡し設計

CLIからだけでなく、Python スクリプトからライブラリとして利用される場合でも正しくパラメータが反映されるよう、以下の設計ルールを遵守します。

### 4.1 設計ルール
1. **設定オブジェクトを経由した引き渡し**:
   CLIからの引数や `config.toml` の値はすべて `AppConfig` などの **設定オブジェクト（データクラス / Pydanticモデル）** にまとめられます。
2. **関数・クラスへのコンストラクタ注入 (DI)**:
   ライブラリ利用者はこの設定オブジェクトをインスタンス化し、パイプライン初期化時や各モジュールの関数へ引数として直接渡します。
3. **グローバルステートの排除**:
   内部処理において `typer` のコンテキストやグローバル変数を直接参照せず、渡された設定オブジェクトのプロパティを読み取ります。

### 4.2 ライブラリ利用時のコード例 (想定)

```python
from pathlib import Path
from audio_transcriber.config import load_config
from audio_transcriber.streaming import AudioStreamPipeline
from audio_transcriber.stt import TranscriberProvider

# 1. 任意のパスにあるカスタムTOML設定ファイルを読み込む
# （引数なしの場合はカレントディレクトリの config.toml が自動で使われます）
cfg = load_config("/path/to/my_custom_settings.toml")

# コード上で動的に設定を上書きすることも可能
cfg.stream.context_max_length = 200
cfg.stream.context_timeout_seconds = 3.0

# 2. パイプラインへの引き渡し (コンストラクタ注入)
transcriber = TranscriberProvider(model_path=Path("model.bin"))
pipeline = AudioStreamPipeline(
    transcriber=transcriber,
    config=cfg.stream,  # 生成した設定オブジェクトを直接渡す
)
```

## 5. 音響イベント検知 (将来対応)

要件仕様書で定義されている「叫び声や大音量ピーク等の音響イベント検知機能」については、将来対応事項として検討したものであり、今回の実装スコープからは除外します。

### 5.1 マルチトラック入力分離
「マイク音トラック」と「ゲーム音・環境音トラック」を完全に別系統で入力・処理する設計を採用します。これにより、ゲーム音を音声認識（STT）に入れてしまうことによるハルシネーションや誤判定を防止します。

### 5.2 イベント検知手法
* **手法 1 (RMS/dBFS解析)**: 軽量な音圧ピーク検知。叫び声や突発ノイズの即時検知。
* **手法 3 (事前学習モデル YAMNet)**: ONNX 版の軽量モデルを用いた笑い声や拍手などの高度な分類検知。
